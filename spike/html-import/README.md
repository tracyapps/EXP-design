# E0 spike — rendered-HTML import

Fixtures and harness for `docs/HTML-IMPORT-CONTRACT.md` §10. Spike code, not app
code: nothing here ships, and none of it is on the app's build path.

Run everything:

    scripts/verify_html_import_spike.sh

Or one at a time: `… fixture1`, `… fixture2`, `… fixture3`.

## What the spike is actually trying to find out

Contract §2 leaves one question open, and it is the one that decides whether E1 is
buildable as designed: **`WKWebView` has no delegate that reports subresource
requests.** Pass 1 has to block everything *and* record what was attempted.
Blocking is solved (`WKContentRuleList`). Recording is not.

So the harness runs four candidate recorders at once and prints which ones caught
what:

| | Recorder | Blind to |
|---|---|---|
| `D` | DOM walk (`src`, `srcset`, `href`, `data`) | anything constructed at runtime |
| `C` | CSSOM walk (`url()`, `@font-face`) | cross-origin stylesheets it cannot read |
| `I` | patched `fetch` / XHR / `sendBeacon` / `Image` | markup-declared resources; a page that grabs the originals first |
| `P` | `PerformanceObserver` on `resource` entries | blocked entries, depending on WebKit version |

The **RECORDER COVERAGE** block at the end of each run is the finding. Any resource
caught by exactly one recorder makes that recorder load-bearing. Any resource in the
server log but caught by *none* is a blind spot that gets named in §4 — the contract
already promises "requests observed during the render window," and that promise has
to keep matching reality.

## Fixture 1 — EXP's own export

Generated, not committed: the runner compiles `SemanticHTMLPackageCheck` and writes
`fixture1-exp-export/Fixture.exph` from the existing golden-fixture document. Every
element carries `data-exp-id`, so round-trip accuracy is measurable against ground
truth instead of eyeballed.

## Fixture 2 — hand-written, not from EXP

`fixture2-handwritten/` — proves the importer is not merely self-consistent with its
own exporter. One media query at 768px and nothing else, so any difference between
the 393 and 1440 imports traces to exactly one rule. Also carries: a font that is
guaranteed to fall back, a gradient, a radius, a shadow, mixed bold/italic runs in
one paragraph, and prose long enough to wrap differently at the two widths — which
is how you catch an importer that re-ran line breaking instead of measuring.

## Fixture 3 — the trust flow

`fixture3-multiorigin/` with three loopback origins on different ports (same host,
different port is still a distinct origin — which also checks the manifest groups by
scheme+host+**port**):

    127.0.0.1:8731  docroot       the document's own origin, pre-allowed
    127.0.0.1:8732  thirdparty    origin A — stylesheet, webfont, image, script
    127.0.0.1:8733  thirdparty-b  origin B — reachable ONLY once A's widget.js runs

Origin B is the important one. `widget.js` is blocked in pass 1, so pass 1 cannot
possibly know B exists. Allow origin A, and B appears. That is §4's iterative-trust
claim, and if it does not reproduce here the two-pass model is wrong and E1 gets
rescoped before it starts.

Also in the fixture, deliberately: `fonts.googleapis.com` so the manifest is not
purely loopback, `bücher.example` (never resolves) so punycode display can be
checked without a network dependency, and a `background-image` inside the phone
media query so a resource requested at **one viewport only** proves the union
manifest.

`brand.woff2` is a **real, valid woff2**, generated by `make-fixture-font.py` — a
synthetic four-glyph font, so no third-party typeface is redistributed, but it
genuinely parses. That distinction is load-bearing. With a broken font file, the
central finding ("the browser fetched it and the manifest never listed it") could
always be waved away as a consequence of the parse failure. It is not: regenerate the
font with the script if it ever needs rebuilding.

## Reading the output

Three things decide E1, and none of them are a green checkmark:

1. **Recorder coverage** — which recorders are load-bearing, and what nothing saw.
2. **Pass 1 purity** — the fixture-3 pass-1 server log must show exactly one
   request. Anything more and the privacy guarantee is not what the contract says.
3. **The iterative case** — pass 2's manifest must contain `:8733` URLs that pass
   1's did not.
